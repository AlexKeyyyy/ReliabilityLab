# Первый срез Элемента: durable inbox и стратегия C

Историческое описание сборки 1.0-5. Для текущего подключения используйте [ELEMENT_HANDOFF.md](ELEMENT_HANDOFF.md).

Реализованы серверные метаданные и HTTP API. Это часть Элемента, без генератора/адаптера Лины и RabbitMQ. A/B, Operations UI, импорт клиентских наблюдений и метрики следующих этапов пока не реализованы. Неподдерживаемые стратегии отклоняются, а не имитируются.

## Адрес и маршруты

Приложение: [Reliability lab-dev](https://app-802542381.1cmycloud.com/applications/Reliability-lab-dev).
База API: `https://app-802542381.1cmycloud.com/applications/Reliability-lab-dev/api/reliability/v1`.

| Метод | Путь | Результат |
|---|---|---|
| GET | /health | Текстовая проверка доступности |
| POST | /runs | Неизменяемая конфигурация прогона C |
| POST | /messages | Устойчивый приём, без создания заказа |
| POST | /operations/{id}/process | Создание заказа или восстановление результата |
| POST | /operations/{id}/retry | Повтор обработки с новым attempt_id |
| GET | /operations/{id} | Согласованное состояние и реальные заказы |
| GET | /operations/{id}/events | Журнал, до 100 записей на страницу, cursor/next_cursor |

Текущий доступ сервиса и данных — только администраторам. Анонимный запрос отвергается. Лёша включил доступ своей существующей учётной записи к HTTP-сервисам приложения. Новые пользователи, администраторы и постоянные ключи доступа агентом не создавались. Для интеграции с Линой далее нужна отдельная настройка служебного доступа.

## Последовательность ручной проверки

1. Авторизоваться штатным способом. Для внешнего клиента получить токен приложения по документации Элемента, положить его в локальную переменную `RELIABILITYLAB_API_TOKEN`.
2. `POST /runs`:

```json
{
  "run_id": "manual_c_001",
  "strategy": "C",
  "scenario": "normal",
  "seed": 101,
  "dataset_id": "manual_v1",
  "fault_plan_id": "none",
  "expected_count": 100,
  "baseline_enabled": false,
  "config": {"http_timeout_ms": 5000, "max_attempts": 3}
}
```

3. `POST /messages`:

```json
{
  "schema_version": 1,
  "operation_id": "manual_c_001_op001",
  "run_id": "manual_c_001",
  "order_id": "ORD-001",
  "attempt_id": "98f6cc29-8024-4fbb-b61a-82f3add67574",
  "amount_minor": 150000,
  "currency": "RUB",
  "created_at": "2026-11-17T00:00:00Z"
}
```

4. `GET /operations/manual_c_001_op001`: RECEIVED, business_effect_count=0.
5. `POST /operations/manual_c_001_op001/process` с телом `{"attempt_id":"84cfe0ca-df18-4db8-b04d-74282d187181"}`: COMPLETED, ссылка на документ в result.order_ref.
6. `POST /operations/manual_c_001_op001/retry` с новым UUID v4: result содержит ту же ссылку, replayed=true.
7. Повторить GET: business_effect_count=1. В events присутствуют BUSINESS_COMMITTED и RESULT_REPLAYED.

Идентификаторы в примерах — синтетические. Для нового отдельного прогона меняйте run_id и operation_id; новый HTTP-вызов получает новый attempt_id. Точный повтор завершённого attempt_id возвращает сохранённый ответ. Тот же ID с другой командой/операцией вызывает 409.

## Сбой и пределы

Прогон со scenario=fail_before_commit вызывает исключение после записи документа внутри транзакции. Первая попытка завершается 500 INJECTED_BEFORE_COMMIT; независимое чтение должно показать ноль заказов. Новый attempt_id успешно создаёт один заказ. Назначение сбоя сохраняется отдельно до бизнес-транзакции, поэтому сбой срабатывает однократно; авария между назначением и выполнением может израсходовать сбой — такой случай не является воспроизводимым экспериментом и должен быть исключён из сравнения.

Сценарии drop_response_after_commit и duplicate_delivery сейчас обозначают режим внешнего клиента: сам сервер ответ не обрывает и сообщения брокера не дублирует. В live-тесте успешный ответ намеренно отбрасывается, после чего retry восстанавливает заказ. Это модель потери ответа, не реальный сетевой отказ.

Сервер не делает вывод об отсутствии заказа по неизвестной ошибке commit. В таком случае возвращается OUTCOME_UNCONFIRMED, а клиенту требуется чтение состояния. Документация упоминает ИсключениеКонфликтБлокировок, но компилятор 10.0.7-28 не распознал этот тип: узкого catch пока нет, возможен общий 500 с требованием сверки результата вместо отдельного 503.

Внешняя транзакция запрещена для методов, которые владеют commit. Заказ, канонический результат, успешная попытка и commit-событие сохраняются вместе. HTTP-ответ отправляется после возврата из транзакционной области. GET берёт разделяемую блокировку операции, чтобы состояние и число заказов не оказались по разные стороны конкурентного commit.

Поле максимальной длины строки в регистрах ограничено платформой 1000 символами. Сохраняемые JSON здесь ограничены конкретной формой DTO и размерами полей. Это не хранилище произвольных больших сообщений. Тело HTTP проверяется на 16 KiB; текущая реализация читает его перед проверкой, поэтому этот предел не является ограничением памяти транспортного уровня. Для внешней нагрузки потребуется лимит шлюза/ограниченное чтение.

Журнал пагинируется по EventId, а не по времени. Между страницами возможны новые записи, поэтому для обновления timeline начинайте чтение с пустого cursor и сортируйте полученные события по occurred_at. Клиентский UNKNOWN не сохраняется вместо серверного COMPLETED.

## Повторный запуск автоматических проверок

Требуется Python 3.10+; сторонние Python-библиотеки для этих проверок не нужны. Тесты создают синтетические записи с префиксом check_, не очищают их и не затрагивают чужие операции.

```sh
export RELIABILITYLAB_API_BASE_URL='https://app-802542381.1cmycloud.com/applications/Reliability-lab-dev/api/reliability/v1'
# RELIABILITYLAB_API_TOKEN задать локально; не помещать значение в README или Git.
make test-live
```

Существующая браузерная сессия администратора тоже позволяет проверять API, если для пользователя включён доступ к HTTP-сервисам. Выполненный агентом прогон использовал такую сессию. Воспроизводимая внешняя команда выше использует штатный Bearer-токен; получение нового служебного ключа в этом этапе не выполнялось.

`make build VERSION=1.0-5` формирует .xasm из текущих исходников, но само по себе не компилирует и не развёртывает приложение. `make validate` проверяет YAML локально. Облачная компиляция и применение — отдельные проверки.

## Выполненная приёмка

Сборка 1.0-5 скомпилирована и применена на 10.0.7-28, задача обновления Completed, приложение Running на точном ID загруженной сборки. Все 15 live-проверок прошли. Проверены приём, конфликты, сохранение заказа, последовательные и конкурентные повторы C, откат до commit, согласованное чтение и модель отбрасывания ответа.

Сырые запросы/ответы без заголовков авторизации сохранены в [element-c-api-1.0-5.json](../experiments/acceptance/2026-11-17/element-c-api-1.0-5.json). Это приёмочные свидетельства, а не результаты сравнительного исследования A/B/C. Принудительное завершение процесса и настоящий сетевой разрыв пока не проверены.

Kafka, собственная 1С:Шина, микросервисная платформа, Kubernetes, тяжёлый observability-стек, внешние платные сервисы и сложная система авторизации — **вне MVP**. Никакой зависимости от корпоративной инфраструктуры, закрытого кода, настоящих заказов и персональных данных.

## 3. Договориться о контракте ДО параллельной разработки

Предложи и согласуй минимальную версионированную схему сообщения, например:

```json
{
  "schema_version": 1,
  "operation_id": "op-000001",
  "order_id": "ORD-001",
  "amount": 1500,
  "created_at": "2026-11-20T10:00:00Z",
  "run_id": "run-001"
}
```

Проектируемые логические операции API (реальные пути в Элементе проверь по документации и приложению):
- `POST /api/messages` — принять и устойчиво сохранить сообщение;
- `POST /api/operations/{id}/process` — выполнить бизнес-обработку;
- `GET /api/operations/{id}` — получить фактическое состояние;
- `POST /api/operations/{id}/retry` — безопасный повтор с тем же ID;
- `GET /api/runs/{id}/metrics` — агрегированные реальные показатели для дашборда.

Обязательные идентификаторы: `operation_id`, `order_id`, `run_id`, `attempt_id`; времена событий фиксировать в UTC. Разделяй `RECEIVED`, `PROCESSING`, `COMPLETED`, `FAILED`, `UNKNOWN`. `UNKNOWN` означает отсутствие достоверного результата, а **не доказанную ошибку**. Определи допустимые переходы состояния и сценарии повторной доставки, в том числе одновременных повторов.

**Критически важно:** сообщение RabbitMQ подтверждается только после того, как выбранная в исследовании точка устойчивой фиксации на стороне получателя действительно достигнута. `publisher confirm`, `consumer ACK`, HTTP 2xx и успешный бизнес-результат — разные вещи. Не обещай end-to-end «exactly once» без доказательства.

## 4. Три сравниваемые стратегии

**A — Naive retry:** при отсутствии ответа адаптер повторяет вызов. В отдельной учебной конфигурации без идемпотентной защиты это может вызвать дубли. Изолируй этот режим от остальных; маркируй его как намеренно небезопасную базовую реализацию, не как «нормальное поведение RabbitMQ».

**B — Check before retry:** при неопределённом исходе сначала запрашиваем состояние операции и затем при необходимости повторяем. Обязательно проверь гонку между запросом состояния и фактическим завершением бизнес-операции; сам по себе такой подход не гарантирует отсутствие дублей.

**C — Idempotent recovery:** повтор с неизменным `operation_id`, устойчивое хранение результата/идентификатора, недопущение повторного бизнес-эффекта и восстановление ответа. Требуется корректность при повторных и конкурентных запросах; если платформа ограничивает атомарность, документируй это, а не заявляй ложную гарантию. Transactional Outbox добавляй только если он действительно нужен для надёжной исходящей публикации, и не превращай его в обязательную лишнюю подсистему.

## 5. Сбои и эксперимент

Минимальные случаи:
1. Нормальная обработка: сообщение → успешный заказ.
2. Ошибка **до** записи заказа.
3. Обработка успела записать заказ, но ответ/подтверждение потеряны (основной кейс).
4. Повторная доставка того же сообщения.
5. Дополнительно при наличии времени: конкурирующие повторы и недоступность HTTP API.

Сначала реализуй **детерминированные управляемые сбои** (`fail_before_commit`, `drop_response_after_commit`, `duplicate_delivery`) и задокументируй, где именно вводится сбой. Если Python-адаптер отбрасывает полученный ответ, честно назови это *моделированием потери ответа*, а не реальным сетевым отказом. Ground truth — фактическое состояние заказа в 1С:Элементе и независимый журнал экспериментального запуска.

Запускать A/B/C на **одинаковом наборе операций и одинаковых условиях**. Для MVP: минимум 3 повтора основных сценариев; стартовая нагрузка 100 сообщений на запуск, затем при работоспособности 500. Сохранять `run_id`, конфигурацию, версии технологий, параметры тайм-аутов, интенсивность сбоев, raw events. Проверять воспроизводимость результатов.

Метрики: доля корректно завершённых бизнес-операций, число лишних бизнес-эффектов/дублей, число случаев UNKNOWN, доля корректно классифицированных исходов, время обнаружения и восстановления, p50/p95 задержек (только где хватает выборки), дополнительное число HTTP-вызовов. Не путать доставку сообщений с выполнением заказа. Для малых выборок не преувеличивать статистическую уверенность.

## 6. Красивый, но реальный MVP и демонстрация

Сделай аккуратный адаптивный экран **ReliabilityLab / Operations** со следующими элементами:
- KPI-карточки: Sent, Received, Completed, Unknown, Duplicate Attempts, Duplicate Business Effects;
- таблица операций со статусами, временем и `operation_id`;
- подробная timeline выбранной операции: Publish → Receive → Persist → Process → Response Lost → Recovery;
- выбор режима A/B/C и сценария; кнопки Demo Run и Recover, если реально подключены к backend;
- график сравнения стратегий из фактически записанных результатов.

Все цифры — **только из backend / файлов реальных запусков**, не захардкоженные для презентации. Для красивого выступления предусмотрите заранее выполненные и сохранённые результаты, чтобы демо не зависело от сети в аудитории. Англоязычные названия и подписи на самом UI. Оформление современное, с аккуратной типографикой и понятной цветовой семантикой; не трать больше 20% усилий на оформление до готовности основных тестов.

Сценарий живого выступления на 2–3 минуты:
1. Отправляем заказ — он создаётся.
2. Включаем сбой **после фиксации заказа, до получения ответа**.
3. Показываем `UNKNOWN`: ответ потерян, но заказ уже существует.
4. В режиме A повтор приводит к риску/фактическому дублю в нашем демонстрационном обработчике.
5. В режиме C запрос с тем же ID восстанавливает результат **без повторного бизнес-эффекта**.
6. Показываем сравнительный график и ограничения исследования.

## 10. Критерии готовности

MVP считается готовым **только если**:
- RabbitMQ реально передаёт сообщение в HTTP API приложения на Элементе;
- в Элементе появляется настоящий заказ и история операции;
- управляемо воспроизводится сбой «заказ создан, ответ потерян»;

- Лина может повторить запуск по README без ручного изменения кода;
- дашборд и графики используют реальные данные;
- англоязычная статья, материалы выступления и комплект отправки готовы до 30 ноября.

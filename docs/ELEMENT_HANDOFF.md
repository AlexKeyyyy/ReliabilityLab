# Подключение адаптера Лины к ReliabilityLab

Рабочий контракт стороны Элемента. Владелец приложения и API — Лёша. Генератор, RabbitMQ, адаптер и экспериментальный runner — часть Лины. После подключения нужен совместный прогон, чтобы проверить переходы между компонентами и согласовать обработку ошибок доставки.

## Адрес и проверка доступа

```sh
export RELIABILITYLAB_API_BASE_URL='https://app-802542381.1cmycloud.com/applications/Reliability-lab-dev/api/reliability/v1'
# В локальном окружении задать RELIABILITYLAB_CLIENT_ID и RELIABILITYLAB_CLIENT_SECRET
# или RELIABILITYLAB_API_TOKEN, если токен приложения уже получен.
make test-live
```

Проверки создают синтетические прогоны `check_*` и заказы на dev. Им нужны Python и HTTPS-доступ к приложению. При разработке можно выполнить `python3 -m unittest discover -s tests -v` с теми же переменными.

Приложение выдаёт `id_token` по `POST {адрес приложения}/sys/token` с формой `grant_type=CLIENT_CREDENTIALS` и HTTP Basic из отдельной пары Client ID/Secret приложения. Дальше передавайте `Authorization: Bearer …` в `/api/reliability/v1`. Храните токен в памяти, при `401` обновите его. При `403` проверьте права и доступ к HTTP-сервисам. Администратор dev выдаёт ключ служебному пользователю с правом вызова API и передаёт пару по защищённому каналу. У текущей конфигурации API право вызова ограничено администраторами dev. Ключ приложения и ключ панели управления различаются. [Официальная схема аутентификации](https://1cmycloud.com/console/help/element/10.0/docs/topics/external-program-authentication/)

## Запись и восстановление

Все пути относительны к `RELIABILITYLAB_API_BASE_URL`. Для POST используйте `Content-Type: application/json`.

| Действие | Запрос | Успешный ответ |
|---|---|---|
| Зарегистрировать прогон | `POST /runs` | `201` новый прогон, `200` точный повтор, `409 RUN_CONFIG_CONFLICT` при изменении |
| Принять бизнес-сообщение | `POST /messages` | `201` новый inbox, `200` повтор, `durable_stage: INBOX_PERSISTED` |
| Начать обработку | `POST /operations/{id}/process` с `{"attempt_id":"<uuid-v4>"}` | `200`, `durable_stage: BUSINESS_COMMITTED`, `result.order_ref` |
| Повторить обработку | `POST /operations/{id}/retry` с новым `attempt_id` | Та же бизнес-операция. Стратегия определяется прогоном |
| Сверить факт заказа | `GET /operations/{id}` | `server_state`, `last_attempt_outcome`, `business_effect_count`, `orders[]` |
| Прочитать события | `GET /operations/{id}/events?cursor=…` | `event_id`, цепочка попыток, серверные события и курсор |
| Получить операции прогона | `GET /runs/{id}/operations?cursor=…` | Уникальные операции с `server_state` и `next_cursor` |
| Получить серверные метрики | `GET /runs/{id}/metrics` | Полученные и завершённые операции, заказы, повторы и дубли |

Пример регистрации прогона B. Для C укажите `baseline_enabled: false`, для обоих учебных режимов A/B — `true`. Для независимого прогона нужен новый `run_id`.

```json
{
  "run_id": "pair001_b",
  "strategy": "B",
  "scenario": "drop_response_after_commit",
  "seed": 101,
  "dataset_id": "set001",
  "fault_plan_id": "drop001",
  "expected_count": 100,
  "baseline_enabled": true,
  "config": {"http_timeout_ms": 5000, "max_attempts": 3}
}
```

```json
{
  "schema_version": 1,
  "operation_id": "pair001_b_op001",
  "run_id": "pair001_b",
  "order_id": "ORD-001",
  "attempt_id": "c298f5d0-03ca-4c78-b4cb-b699781d9872",
  "amount_minor": 150000,
  "currency": "RUB",
  "created_at": "2026-11-23T10:00:00Z"
}
```

Сохраняйте неизменными `operation_id` и бизнес-поля при повторной доставке. `operation_id` глобально уникален, поэтому в сравниваемых прогонах используйте разные ID операций при том же наборе внешних заказов. ID до 96 символов из `[A-Za-z0-9_-]`. Сумма в копейках, целое от 1 до 999999999999. Время UTC с `Z`, допускаются до 3 знаков дробной секунды. На каждый новый POST обработки или приёма — новый глобально уникальный UUID v4 в нижнем регистре. Точное повторение уже завершённого `attempt_id` с той же командой возвращает сохранённый ответ. Другие команда, операция или содержимое конфликтуют.

| Режим | Решение адаптера при неопределённом исходе | Что делает Элемент |
|---|---|---|
| A | Повтор без чтения состояния | Новый HTTP attempt может создать второй заказ |
| B | GET, затем повтор только если заказ не обнаружен | Состояние читается согласованно. Если исходный запрос зафиксирует заказ после GET, решение о повторе уже устарело и возможен дубль |
| C | Сверка результата и безопасный повтор с тем же `operation_id`, если необходим | Заказ и результат фиксируются вместе. Новый attempt возвращает сохранённый результат при наличии заказа |

Планируемый `consumer ACK` — после достоверного `BUSINESS_COMMITTED` с `order_ref` или независимого GET, который подтвердил сохранённый заказ для этой операции. `INBOX_PERSISTED` подтверждает только приём. Если ответ потерян, отмечайте `UNKNOWN` в журнале наблюдателя. Если лимит исчерпан, сохраняйте unresolved по вашему протоколу очереди ошибок. Применение ACK подтверждается только совместным RabbitMQ-прогоном.

`400`, `413`, `415` и `409 *_CONFLICT` требуют исправления входа. `409 ATTEMPT_IN_PROGRESS`, тайм-аут и `500 OUTCOME_UNCONFIRMED` оставляют исход неопределённым. Не выводите отсутствие заказа из HTTP-кода. `500 INJECTED_BEFORE_COMMIT` относится к откату конкретной попытки. Её результат может сосуществовать с заказом от другой попытки. Ошибки самого шлюза могут иметь другой формат, чем `{ "error": { "code", "message", "retryable" } }`.

## Сбои и данные для статьи

- `normal` — базовый прогон. `fail_before_commit` — однократное исключение в бизнес-транзакции, после записи документа и до фиксации. Повтор с новым `attempt_id` проверяет восстановление.
- `drop_response_after_commit` — адаптер отбрасывает подтверждённый успешный ответ до его передачи своей логике восстановления. Фиксируйте это как моделируемую потерю ответа. `duplicate_delivery` — runner воспроизводит повтор сообщения, сохраняя бизнес-содержимое.
- Для проверки окна гонки B зафиксируйте последовательность GET без заказа → commit исходной попытки → повтор по устаревшему GET. Повторите с C на тех же входных данных и сравните ссылки на заказы.
- Для завершённого прогона соберите все страницы `/runs/{id}/operations` и `/operations/{id}/events`, затем прочитайте `GET /operations/{id}` для фактических заказов. Курсоры возвращаются сервером. Размер страницы 100. Между страницами новых данных действуют обычные ограничения курсорного чтения. Выгружайте после завершения записей. Сортируйте события для ленты по `occurred_at`, ответы журнала идут по ID.
- `received` — число строк inbox, `completed` — число операций с заказом, `duplicate_business_effects` — лишние документы, `duplicate_attempts` — process/retry сверх первой попытки для каждой операции. Одинаковый `attempt_id`, повторённый на HTTP, повторно в счётчик не входит.
- `sent` и `unknown` приходят из независимого журнала адаптера. При `observation_coverage: SERVER_ONLY` Элемент возвращает для них `null`. Связывайте журналы по `run_id`, `operation_id`, `attempt_id`. Задержки измеряйте монотонными часами runner. Сохраните версию сборки, набор данных, план сбоев, raw events и список фактических заказов для каждого прогона.

Первый совместный прогон считается успешным, если одна реальная доставка RabbitMQ приводит к одному документу, повторы C возвращают тот же `order_ref`, а из журналов видно, когда адаптер получил подтверждение и отправил ACK.

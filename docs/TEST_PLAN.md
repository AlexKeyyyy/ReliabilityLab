# Приёмочные проверки части Элемента

Статус на 23 ноября. 19 прямых проверок прошли на 1.0-13. Список ниже описывает полную матрицу, включая ещё открытые сценарии. Результаты опубликованы в [приёмке A/B/C](../experiments/acceptance/2026-11-23/element-abc-api.json). Штатный Bearer для служебного пользователя, остановка процесса и проверка с RabbitMQ остаются открытыми.

| № | Действие | Проверяемый результат |
|---|---|---|
| 1 | Публикация и штатный токен | Без доступа 401/403, с разрешённым пользователем API доступен |
| 2 | Принять сообщение | Одна операция RECEIVED, заказов нет; повторное чтение в новом запросе видит запись |
| 3 | Принять то же сообщение дважды и одновременно | Одна запись операции, исходное содержание сохранено |
| 4 | Изменить сумму/order_id/run_id при прежнем operation_id | 409, исходная операция и заказ не изменились |
| 5 | Некорректные JSON, версия, сумма, ID, время | Управляемый 4xx, отсутствуют частично сохранённые данные |
| 6 | Обработать C | Один заказ, COMPLETED, сохранённая ссылка и BUSINESS_COMMITTED |
| 7 | Повторить C с новым AttemptId | Та же ссылка, REPLAYED, число заказов остаётся 1 |
| 8 | Повторить завершённый AttemptId / изменить его команду | Сохранённый ответ / 409; нового эффекта нет |
| 9 | Два одновременных process C | Один эффект; второй ответ — replay либо диагностируемый конфликт блокировки с последующим успешным replay |
| 10 | Исключение в T2 после записи заказа, до commit | Нет заказа, нет COMPLETED и commit-события; подтверждённая ошибка попытки записана вне откатившейся транзакции |
| 11 | Повтор после известного отката | Один успешный эффект, история ошибки сохранена |
| 12 | Прервать обработку до commit, затем новый C | Старый STARTED не вызывает вечную блокировку; новый запрос безопасно создаёт один заказ |
| 13 | Прервать после commit до получения клиентом результата | GET и новый C восстанавливают прежний заказ, эффект не повторяется |
| 14 | Вызвать транзакционный бизнес-метод внутри внешней транзакции | Явный отказ, отсутствие ложного утверждения о commit |
| 15 | Повтор A после моделирования потери ответа | Два разных документа для одного OperationId; baseline явно включён |
| 16 | B после уже завершённого исходного вызова | Чтение обнаруживает заказ, дополнительный process не вызывается |
| 17 | Гонка B: чтение до commit старого запроса и повтор | Зафиксирован допустимый дубль; этот результат не объявляется гарантированно предотвращаемым B |
| 18 | Попытка сменить стратегию/план сбоев работающего прогона | 409, режим C не превращается в baseline |
| 19 | Повторная доставка / больше лимита повторов | Уникальные попытки учтены; нет бесконечного цикла и тихой потери unresolved |
| 20 | Импорт наблюдения клиента дважды | Один EventId; другой payload того же EventId — 409; серверный COMPLETED не изменён |
| 21 | KPI без клиентских наблюдений | Sent/Unknown = N/A; серверные показатели соответствуют прямым запросам по заказам |
| 22 | Повторные и ошибочные попытки после завершения | Сохраняется факт существования заказа, не подменяется FAILED последней попытки |

Для каждого прогона сохранять версии сборки/контракта, RunId, IDs операций/попыток, конфигурацию, исходные HTTP-коды и тела без секретов, независимый список ссылок на заказы и события. Ошибки конкуренции не скрывать автоматическими бесконечными повторами.

Первый этап достаточно завершить проверками 1–14 прямыми HTTP-запросами. Проверки 15–22 добавляются вместе со стратегиями, fault injection и UI. Полный Python/RabbitMQ-прогон — совместная проверка с Линой; Element-only запуск не выдаётся за end-to-end.

Минимум исследования из спецификации: 100 операций, одинаковый dataset/fault plan для A/B/C, по 3 повтора основного сценария. Масштаб 500 — после работоспособности. Для C дополнительно проверять конкуренцию одной операции. Утверждение о корректности ограничивается проверенными сценариями и условиями.
